# 对话式工作流

用途：把旧版 PDT 的对话推进方式迁入当前 TypeScript 内核，避免技能退化为只会提示用户运行 CLI 的工具。

## 核心规则

1. 默认单节点推进：`自动初始化 -> 原始资料处理（如有）-> 对话澄清（如有）-> 功能清单 -> 原型 -> 复杂度评估 -> PRD -> 标注 -> 一致性检查`。
2. `功能清单`、原型、`PRD`、标注完成后必须暂停，等待用户明确确认。
3. 用户提出修改意见时，优先修当前节点，不越级生成后续产物。
4. 新项目少追问，能从需求推断的项目名、类型、业务对象、关键页面和审批流开关应先自动补齐。
5. 回复必须包含当前节点、产物路径、本轮摘要、待确认点和下一步建议。

## 自动初始化

首次收到用户需求时，在进入功能清单之前，先自动完成项目目录初始化：

1. 从需求内容推断项目目录名，使用英文短横线命名（如 `contract-approval`、`hr-onboarding`）。
2. 在当前工作目录下创建 `<project-name>/`、`<project-name>/output/` 和 `<project-name>/raw-materials/` 目录。
3. 将用户原始需求写入 `<project-name>/input.md`。
4. 生成空的 `<project-name>/project-state.json`。
5. 如果推断的目录已存在，直接复用，不覆盖已有文件。
6. 如果用户在对话中提供了附件（截图、文档、表格等），将其保存到 `<project-name>/raw-materials/` 目录。
7. 初始化完成后，在回复中告知用户已创建的目录路径。如果检测到原始资料，进入原始资料处理节点；否则直接进入功能清单节点。

初始化回复示例（无原始资料）：

```markdown
当前节点：自动初始化
产物：
- contract-approval/input.md（已写入需求原文）
- contract-approval/project-state.json（空状态）
- contract-approval/raw-materials/（原始资料目录，当前为空）
- contract-approval/output/（输出目录）

已自动创建项目工作目录，正在进入功能清单整理...
```

初始化回复示例（有原始资料）：

```markdown
当前节点：自动初始化
产物：
- procurement-approval/input.md（已写入需求原文）
- procurement-approval/project-state.json（空状态）
- procurement-approval/raw-materials/（已保存 3 份原始资料）
- procurement-approval/output/（输出目录）

已自动创建项目工作目录，检测到原始资料，正在进入资料处理...
```

## 原始资料处理

当 `raw-materials/` 目录中存在文件时，在进入功能清单之前，先完成原始资料处理：

1. 逐份读取 `raw-materials/` 中的所有文件。
2. 根据文件类型采用不同策略提取信息：
   - **图片**（`.png`/`.jpg`/`.jpeg`/`.gif`/`.webp`）：通过 AI 视觉能力识别图中的文字、流程图、表格等内容，提取角色、流程、规则等关键信息。
   - **Word 文档**（`.docx`/`.doc`）：读取文档全文，提取业务规则、流程描述、角色定义、字段说明等。
   - **Excel 表格**（`.xlsx`/`.xls`）：读取表格数据，提取枚举值、配置项、数据字典、阈值规则等。
   - **PDF 文档**：读取文档内容，提取业务规则、流程说明、制度条款等。
   - **Markdown / 纯文本**（`.md`/`.txt`）：直接读取，提取结构化信息。
3. 将每份资料的关键信息整理成结构化摘要，包含：提取到的角色、流程步骤、业务规则、字段定义、阈值条件、特殊约束等。
4. 标注每条信息的来源文件，确保可追溯。
5. 识别出资料中存在但需求文本中未提及的补充信息。
6. 识别出资料和需求文本之间的矛盾或冲突。
7. 整理完成后暂停，向用户展示摘要和待确认问题，等待用户确认。

原始资料处理回复示例：

```markdown
当前节点：原始资料处理
已读取 3 份原始资料：

1. 聊天记录截图（chat-screenshot.png）
   - 提取到：采购流程为「需求部门提交 → 采购部审核 → 总经理审批」
   - 提取到：金额超过 10 万元需要总经理审批
   - 提取到：当前用 Excel 管理，经常丢失审批记录

2. 采购管理制度（procurement-policy.docx）
   - 提取到：采购分为「日常采购」和「项目采购」两类
   - 提取到：日常采购 5000 元以下部门经理审批即可
   - 提取到：项目采购需要附带招标文件

3. 供应商名单（supplier-list.xlsx）
   - 提取到：共有 23 家供应商，分为 A/B/C 三个等级
   - 提取到：A 级供应商可免招标

基于原始资料，我整理了以下信息，需要你确认：
1. 采购类型：日常采购（5000 元以下部门经理审批）+ 项目采购（需招标文件）
2. 审批路径：需求部门 → 采购部 → 总经理（超 10 万）/ 采购部直接审批（未超 10 万）
3. 供应商管理：A/B/C 三级，A 级免招标

还有几个问题需要澄清：
1. 项目采购的招标文件是必须上传还是可选？
2. 供应商等级由谁来评定和维护？
3. 采购完成后需要生成什么单据？

请确认以上信息是否准确，并回答待澄清问题。
```

## 对话澄清

原始资料处理完成后（或没有原始资料时直接从自动初始化后），如果存在以下情况，进入对话澄清：

1. 原始资料中提取到的信息与需求文本存在矛盾。
2. 原始资料中提到了需求文本未覆盖的关键业务规则。
3. 需求文本中存在模糊表述，需要明确具体参数（如阈值金额、审批节点数量、角色范围等）。
4. 缺少阻塞功能清单生成的关键信息（如核心业务对象不明确、状态机缺少终态定义等）。

澄清原则：
- **一次只问一个问题**，不要一次性抛出多个问题让用户批量回答。
- **优先给选项**：用多选题或带默认值的确认题代替开放式提问，降低用户回答成本。
- 能从已有信息推断的不问。
- 不阻塞当前节点的细节留到后续节点再确认。
- 最多补问 3 轮，每轮 1 个问题。3 轮后仍有未确认信息，用默认值兜底并告知用户。
- 用户回答后立即处理，再问下一个问题（如有）。

澄清回复示例（逐个提问）：

```markdown
当前节点：对话澄清

项目采购的招标文件是必须上传还是可选？

A. 必须上传，否则无法提交（推荐）
B. 可选，不上传也可以提交
C. 根据采购类型决定

请回复选项编号或自定义说明。
```

用户回答后，处理结果并问下一个：

```markdown
收到，招标文件设为必须上传。

下一个问题：供应商等级由谁评定和维护？

A. 采购部在管理后台维护（推荐）
B. 供应商自行填写，采购部审核
C. 系统根据历史数据自动评定

请回复选项编号或自定义说明。
```

所有关键信息确认后，汇总确认结果并进入功能清单节点。

## 功能清单

对话澄清完成后（或无需澄清时直接从原始资料处理后），进入功能清单整理。

### 多方案提议

当需求存在多种可行的实现路径时，必须在功能清单中提出 2-3 种方案并给出推荐：

- **方案描述**：每种方案用 2-3 句话说明核心思路。
- **优劣对比**：列出每种方案的优势和劣势。
- **推荐方案**：明确推荐哪种方案，说明推荐理由。
- **用户决策**：等待用户选择后再确定功能清单内容。

适用场景举例：
- 审批流设计：简单流转 vs 带条件分支的状态机 vs 多级嵌套审批
- 数据管理：单表 vs 主子表 vs 关联表
- 权限模型：角色级权限 vs 数据级权限 vs 混合模式
- 页面结构：单页 Tab 切换 vs 多页面跳转 vs 抽屉/弹窗详情

如果需求路径唯一（没有合理替代方案），直接给出功能清单，不需要强行凑方案。

### 功能清单回复示例

```markdown
当前节点：功能清单

需求存在两种可行方案：

**方案 A：简单流转模式（推荐）**
- 审批流为线性：提交 → 主管审批 → 财务复核 → 完成
- 优势：实现简单，用户理解成本低
- 劣势：不支持条件分支，扩展性有限

**方案 B：状态机模式**
- 审批流带条件分支：金额 < 5000 走快速通道，≥ 5000 走完整审批
- 优势：灵活，支持未来扩展
- 劣势：实现复杂度高，用户需要理解状态概念

推荐方案 A，理由：当前需求为单模块功能，审批路径固定，简单流转已满足需求。状态机可作为后续扩展。

请确认使用哪种方案，或提出修改意见。
```

用户确认方案后，输出完整功能清单并等待确认。

## 复杂度评估

原型完成后，在生成 PRD 之前，自动执行需求复杂度评估：

1. 根据需求涉及的页面数量、审批流复杂度、角色数量、外部系统依赖、数据迁移等因素，评估需求级别为 S / M / L。
2. 评估结果包含：级别（S/M/L）、判定理由、评估因素列表。
3. 评估完成后暂停，向用户展示评估结果和建议使用的 PRD 模板，等待用户确认。
4. 用户可以接受建议级别，也可以手动指定其他级别。
5. 确认后进入 PRD 生成节点，使用对应级别的模板。

S/M/L 级别定义：

- **S 级（轻量需求）**：单页面/单字段改动、不改变核心流程、不涉及审批流/外部系统/复杂权限。PRD 使用轻量需求卡模板（8 个章节）。
- **M 级（中等复杂度）**：单模块新功能或多页面联动、局部流程调整、涉及权限/导入导出/报表/外部接口。PRD 使用功能版模板（17 个章节）。
- **L 级（大型复杂需求）**：跨多个业务系统、核心主数据、复杂审批流/状态机、数据迁移、第三方强依赖、性能/安全/合规要求。PRD 使用完整版 B 端 PRD 模板（21 个章节）。

复杂度评估回复示例：

```markdown
当前节点：复杂度评估
评估结果：M 级（中等复杂度）

判定理由：
- 涉及单模块新功能（费用报销）
- 涉及审批流（主管审批 → 财务复核）
- 涉及 3 个角色（员工、主管、管理员）
- 涉及导入导出（管理员导出报销单）

建议使用 M 级功能版 PRD 模板，包含 17 个章节，覆盖页面、模块、字段、动作、权限、状态机等。

请确认使用 M 级模板，或指定其他级别（S/L）。
```

## 推荐回复结构

```markdown
当前节点：功能清单
产物：workspace/功能清单.md
摘要：已补齐业务对象、状态机、关键页面和待确认问题。
请确认是否继续生成原型；如需修改，请直接指出模块或规则。
```

## 增量修改

当用户在任意节点提出修改意见时，执行以下流程：

### 第一步：识别修改类型

| 修改对象 | 影响范围 | 是否需要回退 |
|----------|----------|-------------|
| 功能清单内容 | 原型 → PRD → 标注 → 一致性检查 | 全部回退 |
| 原型页面/模块/字段 | PRD → 标注 → 一致性检查 | 部分回退 |
| PRD 某个 section | 标注 → 一致性检查 | 部分回退 |
| 标注某个模块 | 一致性检查 | 最小回退 |
| 不涉及上游的纯文案修改 | 无 | 无需回退 |

### 第二步：展示影响并等待确认

向用户明确说明：
1. 修改了什么
2. 哪些下游产物会受影响（dirty 标记）
3. 推荐的处理方式（自动重生成 vs 手动处理）

### 第三步：执行修改

修改上游产物后：
- 如果用户选择自动重生成：按依赖顺序重新生成所有 dirty 产物，跳过中间 HARD-GATE，但最终产物需要用户确认
- 如果用户选择手动处理：只修改指定产物，dirty 产物在下次一致性检查时会提示过期

### 增量修改回复模板

```markdown
当前节点：增量修改 — PRD

已修改：
- 报销金额上限从 500,000 改为 1,000,000
- 更新了字段校验规则 section

受影响产物：
- ⚠️ 标注（需更新金额阈值描述）
- ⚠️ 一致性检查（需重新执行）

正在重新生成标注...
[标注生成完成后]
标注已更新，编号稳定（未新增/删除标注）。

正在执行一致性检查...
[检查完成后]
一致性检查通过，0 错误 1 警告（金额字段精度 warning 已有）。

请确认修改结果。
```

## 变更模式

当用户需求涉及"已上线功能"的修改时，走变更模式而非完整流程。

### 触发条件

满足以下任一条件时进入变更模式：

1. 用户提到已有项目名或已有功能名（如"在报销模块上""合同功能需要改"）
2. 输入中包含变更语义词：修改、调整、增加XX节点、去掉、改为、升级、优化
3. 当前工作目录下已存在同名项目（`<project>/project-state.json` 存在且 `lifecycleStatus` 非 `"draft"`）

### 变更模式流程

**第一步：读取项目状态**

读取已有 `project-state.json`，向用户展示当前功能概要：

- 当前有哪些页面和模块
- 当前状态机有哪些状态和流转
- 当前审批流有几个节点
- 当前有哪些角色和权限

**第二步：识别变更点**

从用户描述中定位需要变更的实体类型：

| 实体类型 | 变更操作示例 |
|----------|-------------|
| page | 新增页面、删除页面、页面结构调整 |
| module | 新增模块、修改模块交互规则 |
| field | 新增字段、修改字段校验规则、删除字段 |
| action | 新增操作、修改操作条件、禁用操作 |
| transition | 新增状态流转、修改流转条件、删除流转 |
| permission | 新增角色权限、修改数据权限范围 |
| flow_node | 新增审批节点、删除审批节点、修改审批人 |

**第三步：评估变更影响范围**

根据变更点向上追溯，列出所有受影响的下游产物：

```
字段变更 → 模块页面 → 原型 → PRD(字段/校验) → 标注 → 一致性检查
状态变更 → 状态机 → PRD(状态流转) → 标注(状态面板) → 一致性检查
审批变更 → 审批流 → PRD(审批规则) → 原型(审批页面) → 标注 → 一致性检查
```

向用户展示影响范围，确认是否接受自动重新生成。

**第四步：生成变更说明**

使用 diff 格式生成变更说明，让用户一目了然：

```markdown
变更说明：

### 1. 审批流变更
- 变更前：员工提交 → 主管审批 → 财务复核 → 完成
- 变更后：员工提交 → 主管审批 → 总经理审批（新增）→ 财务复核 → 完成

### 2. 触发条件变更
- 变更前：所有金额均走主管 → 财务两级审批
- 变更后：金额 < 10 万走主管 → 财务两级；金额 ≥ 10 万走主管 → 总经理 → 财务三级

### 3. 影响范围
- ⚠️ 原型：需新增总经理审批页面
- ⚠️ PRD：状态流转、审批规则、字段校验（金额阈值）需更新
- ⚠️ 标注：审批面板标注需新增总经理节点
- ⚠️ 一致性检查：需重新执行（波及部分）
```

**第五步：执行变更**

1. 修改 `project-state.json` 中的变更实体
2. 重新生成受影响的产物
3. 跳过中间 HARD-GATE，但最终产物需要用户确认

**第六步：变更后一致性检查**

仅检查波及部分，不全量重新检查。检查内容：
- 变更后的状态机是否仍然连通
- 变更后的审批流是否有断链
- 变更后的字段引用是否完整
- 变更后的权限矩阵是否一致

### 变更模式回复示例

```markdown
当前节点：变更模式 — 识别变更点

已读取项目状态：contract-approval/project-state.json
当前功能概要：
- 页面：5 个（列表页、创建页、详情页、审批页、合同台账）
- 状态机：6 个状态（草稿、待审批、审批中、已通过、已驳回、已撤回）
- 审批流：3 级（主管 → 法务 → 总经理）
- 角色：4 个（经办人、主管、法务、管理员）

变更识别结果：
- 变更对象：审批流 — 去掉法务审批节点
- 变更类型：审批节点删除

变更说明：
- 变更前：经办人提交 → 主管审批 → 法务审批 → 总经理审批 → 完成
- 变更后：经办人提交 → 主管审批 → 总经理审批 → 完成

影响范围：
- ✅ 功能清单：无需变更
- ⚠️ 原型：法务审批页面移除，审批流程图更新
- ⚠️ PRD：状态流转表、审批规则需更新
- ⚠️ 标注：审批面板标注移除法务节点
- ⚠️ 一致性检查：需重新执行

是否自动重新生成受影响的产物？
A. 是，全部重新生成（推荐）
B. 只更新 PRD 和原型，标注和一致性检查稍后处理
```

### 变更记录归档

每次变更执行后，在 `project-state.json` 中追加变更记录：

```json
      "affectedArtifacts": ["prototype", "prd", "annotation"],
      "userConfirmed": true
    }
  ]
}
```

## 配置变更模式

当用户需求仅涉及枚举值、阈值、权限等配置项变更时，走精简流程。

### 触发条件

满足以下任一条件时进入配置变更模式：

1. 输入中包含配置变更语义：新增选项、新增枚举、修改阈值、调整权限、变更默认值、修改排序
2. 变更范围可明确归类为：字典项增删、数值阈值调整、角色权限增删、默认值修改、排序规则变更

### 配置变更模式流程

**第一步：识别配置变更类型**

| 变更类型 | 关键词 | 输出物 |
|----------|--------|--------|
| 字典项增删 | 新增XX选项、去掉XX类型、增加XX枚举 | 字典配置 SQL + 受影响的下拉框页面清单 |
| 数值阈值调整 | 金额从X改成Y、上限改为、阈值调整 | 阈值变更说明 + 受影响的校验规则清单 |
| 角色权限增删 | 给XX角色增加XX权限、去掉XX的XX权限 | 权限配置清单 + 受影响的功能菜单清单 |
| 默认值修改 | 默认排序改为、默认筛选条件改为 | 默认值变更说明 + 受影响的页面清单 |
| 排序规则变更 | 列表排序改为、优先展示XX | 排序规则变更说明 + 受影响的列表页清单 |

**第二步：定位受影响的页面和功能**

从 `project-state.json` 中反向查找：
- 字典项变更 → 查找所有引用该字典的 field → 找到对应的 page 和 module
- 阈值变更 → 查找包含该阈值的校验规则 → 找到对应的 flow 和 transition
- 权限变更 → 查找该角色的所有 permission → 找到对应的 action 和 page

**第三步：生成配置变更说明**

输出 4 部分内容：

1. **变更内容**：用一句话说清楚改了什么
2. **配置清单**：需要在系统后台执行的具体操作（SQL、配置项、代码修改）
3. **影响范围**：哪些页面、哪些角色受影响
4. **回归测试点**：改完后需要验证什么

## 需求接入模式

当用户已有 PRD 文档或原型，只需要做部分流程时，走接入模式。

### 触发条件

- 用户说"我已经有 PRD 了，只需要做一致性检查"
- 用户说"帮我根据这个 PRD 生成原型"
- 用户说"只需要生成测试用例"
- 用户提供了已有的 PRD/原型/标注文件

### 接入模式流程

**第一步：读取已有产物**

读取用户提供的文件，识别产物类型：

| 文件类型 | 识别方式 | 解析目标 |
|----------|----------|----------|
| PRD 文档 | 包含"需求背景""字段说明""状态流转"等章节标题 | 提取 roles、businessObjects、flows、fields、permissions |
| HTML 原型 | `.html` 文件，包含页面结构 | 提取 pages、modules、fields、actions |
| 标注文件 | 包含标注编号（如 `#A-001`）和模块引用 | 提取 annotations、moduleReferences |
| project-state.json | 直接为 JSON 格式 | 直接导入 |

**第二步：导入到 project-state.json**

将解析结果写入 `project-state.json`：
- 解析 PRD → 写入 prdSpec
- 解析原型 → 写入 prototypeSpec
- 解析标注 → 写入 annotationSpec
- 记录 `lifecycleStatus` 为实际完成的节点

**第三步：前置条件检查**

根据用户要求的节点，检查前置产物是否已具备：

| 目标节点 | 必须具备的前置产物 |
|----------|-------------------|
| 生成原型 | 功能清单（或从 PRD 反推） |
| 生成 PRD | 功能清单 + 原型 |
| 生成标注 | PRD + 原型 |
| 一致性检查 | PRD + 原型 + 标注 |
| 生成测试用例 | PRD（至少） |

如果前置产物缺失，向用户说明缺少什么，提供两个选项：
A. 先生成缺失的前置产物，再执行目标节点
B. 让用户补充缺失的产物文件

**第四步：执行目标节点**

前置条件满足后，正常执行用户要求的节点，走标准的 HARD-GATE 确认流程。

## Bug 修复需求模式

当用户需求属于已上线功能的 Bug 修复时，走精简流程。

### 触发条件

满足以下任一条件时进入 Bug 修复模式：

1. 输入中包含 Bug 语义词：XX不对、XX没生效、XX报错、XX显示异常、XX没反应、修复、fix
2. 用户描述的问题符合"预期行为 vs 实际行为"模式
3. 用户提到具体报错信息或异常截图

### Bug 修复模式流程

**第一步：生成 Bug 修复需求卡**

从用户描述中提取以下信息，如有缺失则逐项补问：

| 字段 | 说明 | 是否必须 |
|------|------|----------|
| 问题描述 | 用一句话说清楚什么功能出了什么问题 | 是 |
| 复现步骤 | 1. 打开XX页面 → 2. 点击XX → 3. 输入XX → 4. 看到异常 | 是 |
| 期望行为 | 正确情况下应该是什么表现 | 是 |
| 实际行为 | 当前的错误表现是什么 | 是 |
| 影响范围 | 影响哪些角色、哪些页面、是否有数据损坏风险 | 是 |
| 严重程度 | 阻断（无法使用）/ 严重（核心功能异常）/ 一般（非核心异常）/ 轻微（显示问题） | 是 |
| 发生频率 | 必现 / 高概率 / 偶发 / 仅特定条件 | 否 |

**第二步：评估修复影响**

分析修复是否涉及以下系统组件：

| 组件 | 检查内容 | 影响评估 |
|------|----------|----------|
| 状态机 | 修复是否改变状态流转逻辑 | 高：需要重新验证所有状态路径 |
| 权限 | 修复是否涉及权限判断 | 高：需要验证各角色权限正确性 |
| 数据一致性 | 修复是否涉及数据写入/更新 | 高：需要验证历史数据不受影响 |
| 前端展示 | 修复是否只影响 UI 展示 | 低：回归测试仅需验证 UI |
| 字段校验 | 修复是否改变校验规则 | 中：需要验证所有校验场景 |

**第三步：生成回归测试点**

基于修复影响范围，生成回归测试清单：
- 核心验证点：修复后 Bug 是否消失
- 副作用验证点：修复是否引入新问题
- 边界验证点：相关功能的边界条件是否正常

### Bug 修复回复示例

```markdown
当前节点：Bug 修复需求模式

**Bug 修复需求卡**

| 字段 | 内容 |
|------|------|
| 问题描述 | 报销单提交后状态未更新，仍显示"草稿" |
| 复现步骤 | 1. 打开报销单列表 → 2. 新建报销单填写金额和附件 → 3. 点击"提交审批" → 4. 提示"提交成功" → 5. 返回列表，状态仍为"草稿" |

| 严重程度 | 阻断（核心审批流程无法启动） |
| 发生频率 | 必现 |

**修复影响评估**
- ⚠️ 状态机：修复涉及状态流转（草稿 → 待审批），需验证所有状态路径
- ✅ 权限：不涉及

2. 已存在的历史"草稿"状态报销单，手动提交后状态正确更新
3. 审批通过/驳回后状态流转正常
4. 撤回后状态正确回退为"草稿"
5. 不同金额的报销单提交后状态均正确更新
```

## 数据迁移需求模式

当用户需求涉及历史数据迁移或批量导入时，走数据迁移流程。

### 触发条件

满足以下任一条件时进入数据迁移模式：

1. 输入中包含迁移语义词：迁移、导入、历史数据、批量导入、数据清洗、数据同步、旧系统
2. 用户提到需要从 Excel/CSV/外部系统导入数据

### 数据迁移模式流程

**第一步：澄清迁移需求**

逐项确认以下信息：

| 确认项 | 说明 |
|--------|------|
| 数据来源 | 哪个系统 / 什么格式的文件 / 多大数据量 |
| 数据目标 | 导入到本系统的哪个模块/表 |
| 数据时间范围 | 全量迁移还是只迁移近几年数据 |
| 数据质量 | 已知的数据质量问题（缺失值、格式不统一、重复数据） |
| 迁移时间窗口 | 是否有停机维护窗口 / 是否允许在线迁移 |
| 回滚要求 | 迁移失败时是否需要回滚到迁移前状态 |

**第二步：生成字段映射表**

源字段 → 目标字段 → 转换规则：

```markdown
| 源字段 | 目标字段 | 类型 | 转换规则 | 必填 | 默认值 |
|--------|----------|------|----------|------|--------|
| 供应商名称 | supplierName | string | 直接映射 | 是 | - |
| 供应商等级 | level | enum | A→战略, B→重要, C→普通 | 否 | C |
| 联系人 | contactPerson | string | 去除首尾空格 | 否 | - |
| 注册日期 | createdAt | date | YYYY/MM/DD → ISO 8601 | 否 | 导入当天 |
```

**第三步：生成数据清洗规则**

| 清洗场景 | 处理方式 |
|----------|----------|
| 必填字段为空 | 标记为异常行，不导入，输出异常报告 |
| 格式不匹配 | 按转换规则尝试自动修复，修复失败则标记异常 |
| 重复数据 | 根据唯一键（如供应商名称+统一社会信用代码）去重 |
| 枚举值不匹配 | 映射到默认值，记录日志 |
| 超长字符串 | 截断到目标字段长度，记录日志 |

**第四步：生成迁移验证方案**

| 验证项 | 验证方式 | 预期结果 |
|--------|----------|----------|
| 数据条数 | 源数据条数 vs 导入成功条数 + 异常条数 | 三者之和相等 |
| 关键字段 | 抽样 5% 比对源数据和目标数据 | 完全一致 |
| 业务规则 | 导入后数据是否满足系统校验规则 | 无校验错误 |
| 关联完整性 | 引用其他主数据的字段是否关联正确 | 外键有效 |

**第五步：生成回滚方案**

- 迁移前：备份目标表数据
- 迁移失败：使用备份数据恢复，清空本次导入数据
- 部分成功：标记已导入批次，支持按批次回滚

```markdown
**字段映射表**
```

## 系统对接需求模式

当用户需求涉及与外部系统对接时，走系统对接流程。

### 触发条件

满足以下任一条件时进入系统对接模式：

1. 输入中包含对接语义词：对接、同步、推送、拉取、集成、XX系统、接口调用
2. 用户提到需要与 ERP/CRM/OA/HR/财务系统等外部系统交互

### 系统对接模式流程

**第一步：需求澄清**

逐项确认对接细节：

| 确认项 | 选项 |
|--------|------|
| 对接系统 | 具体系统名称和版本 |
| 数据流向 | 本系统→对方 / 对方→本系统 / 双向 |
| 同步方式 | 实时推送 / 定时拉取 / 事件触发 / 手动触发 |
| 同步频率 | 实时 / 每小时 / 每天 / 每周 |
| 触发条件 | 状态变更时 / 定时任务 / 用户手动操作 |
| 鉴权方式 | API Key / OAuth / Token / IP 白名单 |
| 数据格式 | JSON / XML / CSV |
| 异常处理 | 对方不可用时：重试 / 告警 / 人工处理 |

**第二步：生成接口对接方案**

```markdown
### 接口清单

| 接口名称 | 方向 | 触发条件 | 数据内容 | 频率 |
|----------|------|----------|----------|------|
| 审批结果推送 | 本系统→财务系统 | 报销单审批通过 | 报销单号、金额、费用类型、付款信息 | 实时 |
| 员工信息同步 | HR系统→本系统 | 每日定时 | 工号、姓名、部门、职级 | 每天 02:00 |
| 凭证生成 | 本系统→财务系统 | 审批通过且付款完成 | 凭证号、借方科目、贷方科目、金额 | 实时 |

### 接口交互流程

1. 本系统检测到触发事件（报销单审批通过）
2. 组装推送数据，按对方系统要求的格式序列化
3. 调用对方系统 API，携带鉴权信息
4. 接收响应：
   - 成功（200）：记录推送日志，标记同步状态为"已同步"
   - 失败（4xx/5xx）：进入重试队列
5. 重试策略：最多重试 3 次，间隔 5 分钟、15 分钟、60 分钟
6. 3 次均失败：告警通知管理员，标记同步状态为"同步失败"
```

**第三步：生成字段映射表**

本系统字段 ↔ 对方系统字段，包含方向和转换规则。

**第四步：异常场景覆盖**

| 异常场景 | 处理方式 |
|----------|----------|
| 对方系统不可用 | 重试 3 次 → 告警 → 人工处理 |
| 数据格式不匹配 | 记录错误日志 → 告警 → 数据修正后重试 |
| 推送失败（网络超时） | 自动重试，幂等保证 |
| 数据冲突（对方已存在同编号） | 对方系统去重逻辑处理 / 本系统标记冲突 |
| 鉴权过期 | 自动刷新 Token → 重试 |
| 对方系统版本升级 | 接口版本兼容方案 + 灰度验证 |

### 系统对接回复示例

```markdown
当前节点：系统对接需求模式

已澄清对接需求：
- 对接系统：公司财务系统（用友 U8）
- 数据流向：报销系统 → 财务系统（单向推送）
- 同步方式：审批通过时实时推送
- 鉴权方式：API Key + IP 白名单

**接口清单**

| 接口名称 | 方向 | 触发条件 | 数据内容 |
|----------|------|----------|----------|
| 报销凭证推送 | 本系统→财务 | 报销单审批通过 | 凭证号、报销单号、金额、费用科目、付款账户 |
```

## 跳步/精简模式

当用户显式要求只做部分流程时，支持跳步执行。

### 触发条件

- 用户说"我已经有 PRD 了，只需要做一致性检查"
- 用户说"我只需要画原型，不需要 PRD"
- 用户说"帮我只生成测试用例"
- 用户说"只需要做标注"、"帮我检查一下 PRD 和原型的一致性"

### 跳步模式流程

**第一步：识别目标节点**

从用户描述中确定要执行的节点。

**第二步：前置条件检查**

每个节点都有前置依赖，跳步时必须验证前置产物是否已具备：

| 目标节点 | 必须具备的前置产物 | 可选前置产物 |
|----------|-------------------|-------------|
| 功能清单 | 用户需求文本 | 原始资料（如有） |
| 原型 | 功能清单（或从 PRD 反推） | — |
| 复杂度评估 | 功能清单 + 原型 | — |
| PRD | 功能清单 + 原型 + 复杂度评估确认 | — |
| 标注 | PRD + 原型 | — |
| 一致性检查 | PRD + 原型 + 标注 | 测试用例（如有） |
| 测试用例 | PRD（至少） | 原型 + 标注（如有可增强覆盖） |
| 业务确认单 | PRD | 原型（如有） |
| 上线交付包 | PRD + 原型 + 一致性检查通过 | — |

**第三步：缺失产物处理**

如果前置产物缺失，提供两个选项：
A. 先自动生成缺失的前置产物，再执行目标节点（推荐）
B. 让用户手动提供缺失的产物文件

**第四步：执行目标节点**

前置条件满足后，正常执行目标节点。跳过的节点不强制走 HARD-GATE，但目标节点的输出仍需用户确认。

### 跳步模式回复示例

```markdown
当前节点：跳步模式 — 一致性检查

已识别目标节点：一致性检查

前置条件检查：
✅ PRD：已找到 contract-approval/output/PRD.md
✅ 原型：已找到 contract-approval/output/prototype.html
✅ 标注：已找到 contract-approval/output/annotated-prototype.html

前置产物完整，可以开始一致性检查。
```

```markdown
当前节点：跳步模式 — 前置产物缺失

已识别目标节点：一致性检查

前置条件检查：
✅ PRD：已找到
❌ 原型：未找到
❌ 标注：未找到

缺少 2 个前置产物。请选择：
A. 先自动生成原型和标注，再执行一致性检查（推荐）
B. 请提供原型和标注文件
```

## 多项目关联

当需求涉及跨模块引用时，识别并处理多项目关联。

### 触发条件

- 用户提到"报销系统需要关联合同系统的合同编号"
- 需求涉及引用其他模块的主数据或业务数据
- 用户明确提到需要跨系统关联

### 处理方式

1. **识别跨项目实体引用**：标记哪些字段引用了外部模块的实体
2. **记录关联关系**：在 `project-state.json` 中记录跨项目引用：
   ```json
   {
     "crossProjectRefs": [
       {
         "sourceField": "contractNo",
         "targetProject": "contract-approval",
         "targetEntity": "object_contract",
         "targetField": "contractNo",
         "refType": "read_only"
       }
     ]
   }
   ```
3. **关联一致性检查**：检查引用的字段名、类型是否与目标项目一致
4. **PRD 标注**：在 PRD 中明确标注跨项目引用的字段和数据来源

### 需求澄清追问

1. 引用外部模块数据时，是只读引用还是需要双向同步？
2. 外部数据变更时，本系统如何感知？（实时同步 / 手动刷新 / 不同步）
3. 外部数据不存在或已停用时，如何处理？

## 需求来源多样化

支持从多种来源提取需求信息。

### 支持的需求来源

| 来源类型 | 输入方式 | 处理策略 |
|----------|----------|----------|
| 自由文本 | 对话框直接输入 | 走标准需求结构化流程 |
| 原始资料文件 | 图片/Word/Excel/PDF/Markdown | 保存到 raw-materials/，提取关键信息 |
| 任务卡片 | Jira/飞书/Linear 导出的 JSON 或 CSV | 解析任务字段，提取需求描述、优先级、负责人 |
| 竞品截图 | 竞品产品截图 | 视觉识别功能点，提取功能差异 |
| 合规文档 | 行业标准/合规要求文档 | 提取约束条件、必须满足的合规要求 |
| 用户反馈汇总 | 用户反馈表格 | 聚类分析高频问题，提取需求点 |

### 任务卡片解析规则

当用户提供 Jira/飞书导出的任务卡片时：

1. 提取字段：标题、描述、优先级、标签、负责人、截止日期
2. 将多个任务卡片聚类为功能模块
3. 按优先级排序，标记紧急任务
4. 从任务描述中提取业务规则和验收标准

### 竞品截图分析规则

当用户提供竞品截图时：

1. 通过 AI 视觉识别截图中的功能模块和交互元素
2. 识别竞品的功能亮点和差异化设计
3. 提取可借鉴的交互模式
4. 标注哪些功能点在当前需求范围内，哪些可作为后续参考

## 优先级排序

功能清单生成后，自动提供优先级建议。

### 优先级矩阵

| 维度 | 评估标准 |
|------|----------|
| 业务影响 | 高：直接影响核心业务流程 / 中：提升效率但不阻断 / 低：体验优化 |
| 实现难度 | 简单：单页面改动 / 中等：多页面联动 / 复杂：跨模块或涉及外部系统 |
| 紧急程度 | 高：用户强烈要求或阻断业务 / 中：计划内需求 / 低：锦上添花 |

### 功能分组建议

基于优先级矩阵，将功能分为三组：

| 分组 | 定义 | 建议 |
|------|------|------|
| MVP（第一期） | 业务影响高 + 实现难度简单或中等 | 必须在第一期交付 |
| 增强（第二期） | 业务影响中 + 实现难度中等 | 第一期上线后 2-4 周内交付 |
| 优化（后续） | 业务影响低 或 实现难度复杂 | 视用户反馈决定是否做 |

### 输出格式

```markdown
## 优先级建议

### MVP（第一期必做）
| 功能 | 业务影响 | 实现难度 | 理由 |
|------|----------|----------|------|
| 报销单创建和提交 | 高 | 简单 | 核心流程，无此功能系统无法使用 |
| 主管审批 | 高 | 简单 | 核心流程，审批流的基础节点 |

### 增强（第二期）
| 功能 | 业务影响 | 实现难度 | 理由 |
|------|----------|----------|------|
| 报销单导出 | 中 | 简单 | 提升管理效率，不影响核心流程 |
| 统计报表 | 中 | 中等 | 数据分析需求，可暂用 Excel 替代 |

### 优化（后续）
| 功能 | 业务影响 | 实现难度 | 理由 |
|------|----------|----------|------|
| 看板视图 | 低 | 复杂 | 体验优化，列表视图已满足需求 |
```

## CLI 定位

- 对普通产品工作，默认不要求用户手动敲命令。
- 对本地复现、批量生成、校验、调试和测试，使用 `pnpm dev -- ...`。
- CLI 输出结果需要转化成产品经理能读懂的摘要，而不是只贴命令日志。
