# 闭环质量检查

用途：把旧版 PDT 的闭环检查清单接到当前 TypeScript 校验与一致性报告思路上。

## 必查项

原型与 PRD：

- 原型中的页面和模块是否都进入 PRD。
- PRD 中的关键规则是否都能在原型找到挂载点。
- 页面文案、按钮动作、弹窗逻辑是否进入 PRD。

状态机：

- 是否定义核心业务对象的完整状态集合。
- 每个状态变化是否有触发动作和允许角色。
- 是否存在终态、取消态、回退态和驳回态。
- 非法流转是否有拦截规则。

审批流：

- 审批流是否只在需要时出现。
- 审批节点、审批角色和可执行动作是否明确。
- 驳回、撤回、转审等能力是否有业务依据。

角色与权限：

- 不同角色的页面、模块、字段、动作可见性是否明确。
- 越权操作是否有隐藏、禁用或错误提示。
- 权限规则是否有测试用例覆盖。

标注与追溯：

- 每个核心模块是否有标注或明确排除原因。
- 标注编号是否稳定。
- 标注是否能追溯到 PRD section、测试用例、权限规则和 DOM 节点。
- 增量修改后，产物清单 hash 是否能发现过期输出。

## 推荐输出

一致性检查采用两阶段审查，必须按顺序完成：

### 第一阶段：PRD 与原型一致性检查

检查 PRD 和原型之间的对应关系，确保没有遗漏或矛盾：

- 原型中的每个页面和模块是否都在 PRD 中有对应说明。
- PRD 中的每个关键规则是否都能在原型中找到挂载点。
- 页面文案、按钮动作、弹窗逻辑是否进入 PRD。
- 状态机定义是否与原型中的状态展示一致。
- 权限规则是否与原型中的角色差异一致。

### 第二阶段：业务规则完整性检查

在第一阶段通过后，检查 PRD 本身的业务规则覆盖度：

- 每个业务流程是否有完整的主流程和异常流程说明。
- 每个关键操作是否有异常处理（网络异常、并发冲突、数据不一致等）。
- 每个业务对象是否有完整的生命周期说明（创建、修改、删除、归档）。
- 每个审批节点是否有驳回、撤回、转审的处理规则。
- 每个数据输入点是否有校验规则（必填、格式、范围、唯一性）。
- 每个列表/查询页面是否有筛选、排序、分页规则。
- 每个导出/导入场景是否有数据格式、大小限制、错误处理说明。

**两阶段审查顺序不可颠倒**：必须先通过第一阶段（一致性），再进入第二阶段（完整性）。第一阶段发现问题时，先修复再进入第二阶段。

一致性报告应优先给出可执行问题：

```markdown
## 闭环质量检查报告

### 第一阶段：PRD 与原型一致性
1. [问题] -> 建议：[修复方案]

### 第二阶段：业务规则完整性
1. [问题] -> 建议：[修复方案]

### 标注追溯性
1. [问题] -> 建议：[修复方案]
```

## 验证先行原则

在声称任何产物"完成"或"通过检查"之前，必须先执行实际验证，用证据支撑结论。

### 铁律

```
没有运行验证命令，不得声称产物通过检查。
```

### 验证流程

在声称产物完成前，必须：

1. **识别**：用什么命令或操作可以验证这个产物？
2. **执行**：运行完整的验证命令（如 `pnpm dev -- check --project ...`）。
3. **阅读**：完整阅读输出，检查是否有错误、警告或遗漏。
4. **确认**：输出是否真的支持"通过"的结论？
   - 否 → 如实报告实际状态和发现的问题
   - 是 → 在声称通过时附上验证证据
5. **只有此时**：才能声称产物通过检查。

### 禁止的表述

以下表述在没有实际验证的情况下禁止使用：

- "应该没问题了"
- "看起来是正确的"
- "我检查过了"（没有附上验证输出）
- "所有检查都通过"（没有运行检查命令）
- "一致性没有问题"（没有逐项核对）

### 正确做法示例

```
✅ 运行 pnpm dev -- check --project xxx/project-state.json
   看到输出：0 errors, 0 warnings
   "一致性检查通过，0 错误 0 警告。"

❌ "一致性检查应该没问题了，所有页面都在 PRD 中有对应。"
```

## 检查失败回退规则

一致性检查发现问题时，按严重程度分级处理：

| 级别 | 处理方式 | 是否需要重新检查 |
|------|----------|-----------------|
| info | 记录建议，不阻断交付 | 否 |
| warning | 自动修复 + 在报告中标记已修复项，用户确认 | 否（已自动修复） |
| critical | 展示问题 + 影响范围 + 建议修复方案，用户确认后执行修复 | 是（至少检查受影响部分） |

### 回退范围判定

- 问题在标注层：只重新生成标注，PRD 和原型不动
- 问题在 PRD 层：重新生成 PRD 对应 section → 标注 dirty → 重新生成标注
- 问题在原型层：重新生成原型 → PRD dirty → 标注 dirty → 全部重新生成
- 问题在功能清单层：最上游变更，全部 dirty

### 重新检查规则

- warning 自动修复后不重新检查
- critical 修复后必须重新执行一致性检查（至少覆盖修复涉及的产物）
- 重新检查最多执行 2 轮；仍有 critical 时停止，向用户报告未解决的问题清单
