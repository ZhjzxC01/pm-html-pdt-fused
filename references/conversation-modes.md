# 入口模式详细流程

用途：定义非默认全流程的各种入口模式的详细触发条件、执行流程和回复示例。

## 变更模式

当用户需求涉及"已上线功能"的修改时，走变更模式而非完整流程。

### 触发条件

满足以下任一条件时进入变更模式：

1. 用户提到已有项目名或已有功能名（如"在报销模块上""合同功能需要改"）
2. 输入中包含变更语义词：修改、调整、增加XX节点、去掉、改为、升级、优化
3. 当前工作目录下已存在同名项目（`<project>/project-state.json` 存在且 `lifecycleStatus` 非 `"draft"`）

### 变更模式流程

**第一步：读取项目状态**

读取已有 `project-state.json`，向用户展示当前功能概要：

- 当前有哪些页面和模块
- 当前状态机有哪些状态和流转
- 当前审批流有几个节点
- 当前有哪些角色和权限

**第二步：识别变更点**

从用户描述中定位需要变更的实体类型：

| 实体类型 | 变更操作示例 |
|----------|-------------|
| page | 新增页面、删除页面、页面结构调整 |
| module | 新增模块、修改模块交互规则 |
| field | 新增字段、修改字段校验规则、删除字段 |
| action | 新增操作、修改操作条件、禁用操作 |
| transition | 新增状态流转、修改流转条件、删除流转 |
| permission | 新增角色权限、修改数据权限范围 |
| flow_node | 新增审批节点、删除审批节点、修改审批人 |

**第三步：评估变更影响范围**

根据变更点向上追溯，列出所有受影响的下游产物：

```
字段变更 → 模块页面 → 原型 → PRD(字段/校验) → 标注 → 一致性检查
状态变更 → 状态机 → PRD(状态流转) → 标注(状态面板) → 一致性检查
审批变更 → 审批流 → PRD(审批规则) → 原型(审批页面) → 标注 → 一致性检查
```

向用户展示影响范围，确认是否接受自动重新生成。

**第四步：生成变更说明**

使用 diff 格式生成变更说明，让用户一目了然。

**第五步：执行变更**

1. 修改 `project-state.json` 中的变更实体
2. 重新生成受影响的产物
3. 跳过中间 HARD-GATE，但最终产物需要用户确认

**第六步：变更后一致性检查**

仅检查波及部分，不全量重新检查。检查内容：
- 变更后的状态机是否仍然连通
- 变更后的审批流是否有断链
- 变更后的字段引用是否完整
- 变更后的权限矩阵是否一致

### 变更记录归档

每次变更执行后，在 `project-state.json` 中追加变更记录：

```json
{
  "changeHistory": [
    {
      "id": "change_001",
      "timestamp": "2026-05-11T10:30:00+08:00",
      "description": "去掉法务审批节点",
      "changeType": "flow_node_delete",
      "affectedArtifacts": ["prototype", "prd", "annotation"],
      "userConfirmed": true
    }
  ]
}
```

## 配置变更模式

当用户需求仅涉及枚举值、阈值、权限等配置项变更时，走精简流程。

### 触发条件

满足以下任一条件时进入配置变更模式：

1. 输入中包含配置变更语义：新增选项、新增枚举、修改阈值、调整权限、变更默认值、修改排序
2. 变更范围可明确归类为：字典项增删、数值阈值调整、角色权限增删、默认值修改、排序规则变更

### 配置变更模式流程

**第一步：识别配置变更类型**

| 变更类型 | 关键词 | 输出物 |
|----------|--------|--------|
| 字典项增删 | 新增XX选项、去掉XX类型、增加XX枚举 | 字典配置 SQL + 受影响的下拉框页面清单 |
| 数值阈值调整 | 金额从X改成Y、上限改为、阈值调整 | 阈值变更说明 + 受影响的校验规则清单 |
| 角色权限增删 | 给XX角色增加XX权限、去掉XX的XX权限 | 权限配置清单 + 受影响的功能菜单清单 |
| 默认值修改 | 默认排序改为、默认筛选条件改为 | 默认值变更说明 + 受影响的页面清单 |
| 排序规则变更 | 列表排序改为、优先展示XX | 排序规则变更说明 + 受影响的列表页清单 |

**第二步：定位受影响的页面和功能**

从 `project-state.json` 中反向查找：
- 字典项变更 → 查找所有引用该字典的 field → 找到对应的 page 和 module
- 阈值变更 → 查找包含该阈值的校验规则 → 找到对应的 flow 和 transition
- 权限变更 → 查找该角色的所有 permission → 找到对应的 action 和 page

**第三步：生成配置变更说明**

输出 4 部分内容：

1. **变更内容**：用一句话说清楚改了什么
2. **配置清单**：需要在系统后台执行的具体操作（SQL、配置项、代码修改）
3. **影响范围**：哪些页面、哪些角色受影响
4. **回归测试点**：改完后需要验证什么

### 配置变更模式不做的事

- 不重新生成原型
- 不重新生成 PRD
- 不重新生成标注
- 不执行一致性检查
- 不创建新版本号

### 配置变更归档

配置变更记录在 `project-state.json` 的 `changeHistory` 中，标记 `changeType` 为配置类型。

## 需求接入模式

当用户已有 PRD 文档或原型，只需要做部分流程时，走接入模式。

### 触发条件

- 用户说"我已经有 PRD 了，只需要做一致性检查"
- 用户说"帮我根据这个 PRD 生成原型"
- 用户说"只需要生成测试用例"
- 用户提供了已有的 PRD/原型/标注文件

### 接入模式流程

**第一步：读取已有产物**

读取用户提供的文件，识别产物类型：

| 文件类型 | 识别方式 | 解析目标 |
|----------|----------|----------|
| PRD 文档 | 包含"需求背景""字段说明""状态流转"等章节标题 | 提取 roles、businessObjects、flows、fields、permissions |
| HTML 原型 | `.html` 文件，包含页面结构 | 提取 pages、modules、fields、actions |
| 标注文件 | 包含标注编号（如 `#A-001`）和模块引用 | 提取 annotations、moduleReferences |
| project-state.json | 直接为 JSON 格式 | 直接导入 |

**第二步：导入到 project-state.json**

将解析结果写入 `project-state.json`：
- 解析 PRD → 写入 prdSpec
- 解析原型 → 写入 prototypeSpec
- 解析标注 → 写入 annotationSpec
- 记录 `lifecycleStatus` 为实际完成的节点

**第三步：前置条件检查**

根据用户要求的节点，检查前置产物是否已具备：

| 目标节点 | 必须具备的前置产物 |
|----------|-------------------|
| 生成原型 | 功能清单（或从 PRD 反推） |
| 生成 PRD | 功能清单 + 原型 |
| 生成标注 | PRD + 原型 |
| 一致性检查 | PRD + 原型 + 标注 |
| 生成测试用例 | PRD（至少） |

如果前置产物缺失，向用户说明缺少什么，提供两个选项：
A. 先生成缺失的前置产物，再执行目标节点
B. 让用户补充缺失的产物文件

**第四步：执行目标节点**

前置条件满足后，正常执行用户要求的节点，走标准的 HARD-GATE 确认流程。

## Bug 修复需求模式

当用户需求属于已上线功能的 Bug 修复时，走精简流程。

### 触发条件

满足以下任一条件时进入 Bug 修复模式：

1. 输入中包含 Bug 语义词：XX不对、XX没生效、XX报错、XX显示异常、XX没反应、修复、fix
2. 用户描述的问题符合"预期行为 vs 实际行为"模式
3. 用户提到具体报错信息或异常截图

### Bug 修复模式流程

**第一步：生成 Bug 修复需求卡**

从用户描述中提取以下信息，如有缺失则逐项补问：

| 字段 | 说明 | 是否必须 |
|------|------|----------|
| 问题描述 | 用一句话说清楚什么功能出了什么问题 | 是 |
| 复现步骤 | 1. 打开XX页面 → 2. 点击XX → 3. 输入XX → 4. 看到异常 | 是 |
| 期望行为 | 正确情况下应该是什么表现 | 是 |
| 实际行为 | 当前的错误表现是什么 | 是 |
| 影响范围 | 影响哪些角色、哪些页面、是否有数据损坏风险 | 是 |
| 严重程度 | 阻断（无法使用）/ 严重（核心功能异常）/ 一般（非核心异常）/ 轻微（显示问题） | 是 |
| 发生频率 | 必现 / 高概率 / 偶发 / 仅特定条件 | 否 |

**第二步：评估修复影响**

分析修复是否涉及以下系统组件：

| 组件 | 检查内容 | 影响评估 |
|------|----------|----------|
| 状态机 | 修复是否改变状态流转逻辑 | 高：需要重新验证所有状态路径 |
| 权限 | 修复是否涉及权限判断 | 高：需要验证各角色权限正确性 |
| 数据一致性 | 修复是否涉及数据写入/更新 | 高：需要验证历史数据不受影响 |
| 前端展示 | 修复是否只影响 UI 展示 | 低：回归测试仅需验证 UI |
| 字段校验 | 修复是否改变校验规则 | 中：需要验证所有校验场景 |

**第三步：生成回归测试点**

基于修复影响范围，生成回归测试清单：
- 核心验证点：修复后 Bug 是否消失
- 副作用验证点：修复是否引入新问题
- 边界验证点：相关功能的边界条件是否正常

## 数据迁移需求模式

当用户需求涉及历史数据迁移或批量导入时，走数据迁移流程。

### 触发条件

满足以下任一条件时进入数据迁移模式：

1. 输入中包含迁移语义词：迁移、导入、历史数据、批量导入、数据清洗、数据同步、旧系统
2. 用户提到需要从 Excel/CSV/外部系统导入数据

### 数据迁移模式流程

**第一步：澄清迁移需求**

逐项确认以下信息：

| 确认项 | 说明 |
|--------|------|
| 数据来源 | 哪个系统 / 什么格式的文件 / 多大数据量 |
| 数据目标 | 导入到本系统的哪个模块/表 |
| 数据时间范围 | 全量迁移还是只迁移近几年数据 |
| 数据质量 | 已知的数据质量问题（缺失值、格式不统一、重复数据） |
| 迁移时间窗口 | 是否有停机维护窗口 / 是否允许在线迁移 |
| 回滚要求 | 迁移失败时是否需要回滚到迁移前状态 |

**第二步：生成字段映射表**

源字段 → 目标字段 → 转换规则。

**第三步：生成数据清洗规则**

| 清洗场景 | 处理方式 |
|----------|----------|
| 必填字段为空 | 标记为异常行，不导入，输出异常报告 |
| 格式不匹配 | 按转换规则尝试自动修复，修复失败则标记异常 |
| 重复数据 | 根据唯一键去重 |
| 枚举值不匹配 | 映射到默认值，记录日志 |
| 超长字符串 | 截断到目标字段长度，记录日志 |

**第四步：生成迁移验证方案**

| 验证项 | 验证方式 | 预期结果 |
|--------|----------|----------|
| 数据条数 | 源数据条数 vs 导入成功条数 + 异常条数 | 三者之和相等 |
| 关键字段 | 抽样 5% 比对源数据和目标数据 | 完全一致 |
| 业务规则 | 导入后数据是否满足系统校验规则 | 无校验错误 |
| 关联完整性 | 引用其他主数据的字段是否关联正确 | 外键有效 |

**第五步：生成回滚方案**

- 迁移前：备份目标表数据
- 迁移失败：使用备份数据恢复，清空本次导入数据
- 部分成功：标记已导入批次，支持按批次回滚

## 系统对接需求模式

当用户需求涉及与外部系统对接时，走系统对接流程。

### 触发条件

满足以下任一条件时进入系统对接模式：

1. 输入中包含对接语义词：对接、同步、推送、拉取、集成、XX系统、接口调用
2. 用户提到需要与 ERP/CRM/OA/HR/财务系统等外部系统交互

### 系统对接模式流程

**第一步：需求澄清**

逐项确认对接细节：

| 确认项 | 选项 |
|--------|------|
| 对接系统 | 具体系统名称和版本 |
| 数据流向 | 本系统→对方 / 对方→本系统 / 双向 |
| 同步方式 | 实时推送 / 定时拉取 / 事件触发 / 手动触发 |
| 同步频率 | 实时 / 每小时 / 每天 / 每周 |
| 触发条件 | 状态变更时 / 定时任务 / 用户手动操作 |
| 鉴权方式 | API Key / OAuth / Token / IP 白名单 |
| 数据格式 | JSON / XML / CSV |
| 异常处理 | 对方不可用时：重试 / 告警 / 人工处理 |

**第二步：生成接口对接方案**

包含接口清单、接口交互流程、重试策略。

**第三步：生成字段映射表**

本系统字段 ↔ 对方系统字段，包含方向和转换规则。

**第四步：异常场景覆盖**

| 异常场景 | 处理方式 |
|----------|----------|
| 对方系统不可用 | 重试 3 次 → 告警 → 人工处理 |
| 数据格式不匹配 | 记录错误日志 → 告警 → 数据修正后重试 |
| 推送失败（网络超时） | 自动重试，幂等保证 |
| 数据冲突（对方已存在同编号） | 对方系统去重逻辑处理 / 本系统标记冲突 |
| 鉴权过期 | 自动刷新 Token → 重试 |
| 对方系统版本升级 | 接口版本兼容方案 + 灰度验证 |

## 跳步/精简模式

当用户显式要求只做部分流程时，支持跳步执行。

### 触发条件

- 用户说"我已经有 PRD 了，只需要做一致性检查"
- 用户说"我只需要画原型，不需要 PRD"
- 用户说"帮我只生成测试用例"
- 用户说"只需要做标注"、"帮我检查一下 PRD 和原型的一致性"

### 跳步模式流程

**第一步：识别目标节点**

从用户描述中确定要执行的节点。

**第二步：前置条件检查**

每个节点都有前置依赖，跳步时必须验证前置产物是否已具备：

| 目标节点 | 必须具备的前置产物 | 可选前置产物 |
|----------|-------------------|-------------|
| 功能清单 | 用户需求文本 | 原始资料（如有） |
| 原型 | 功能清单（或从 PRD 反推） | — |
| 复杂度评估 | 功能清单 + 原型 | — |
| PRD | 功能清单 + 原型 + 复杂度评估确认 | — |
| 标注 | PRD + 原型 | — |
| 一致性检查 | PRD + 原型 + 标注 | 测试用例（如有） |
| 测试用例 | PRD（至少） | 原型 + 标注（如有可增强覆盖） |
| 业务确认单 | PRD | 原型（如有） |
| 上线交付包 | PRD + 原型 + 一致性检查通过 | — |

**第三步：缺失产物处理**

如果前置产物缺失，提供两个选项：
A. 先自动生成缺失的前置产物，再执行目标节点（推荐）
B. 让用户手动提供缺失的产物文件

**第四步：执行目标节点**

前置条件满足后，正常执行目标节点。跳过的节点不强制走 HARD-GATE，但目标节点的输出仍需用户确认。

## 恢复模式

当用户要继续之前中断的项目时，走恢复模式。

### 触发条件

满足以下任一条件时进入恢复模式：

1. 用户说"继续上次的项目"或"继续 XX 项目"
2. 用户进入一个已存在 `project-state.json` 且 `lifecycleStatus` 非 `draft` 的项目目录
3. 用户提到一个当前工作目录下已存在的项目名

### 恢复模式流程

**第一步：读取项目状态**

读取 `<project>/project-state.json`，提取：
- `lifecycleStatus`：当前断点位置
- 已生成的产物清单
- `changeHistory`：上次变更记录
- 上次修改时间

**第二步：展示进度摘要**

```markdown
当前节点：恢复模式

已找到项目：contract-approval
当前进度：prototype_done（原型已确认）
已完成产物：
- ✅ input.md
- ✅ 功能清单
- ✅ 原型（index.html）
- ⬜ PRD（未生成）
- ⬜ 标注（未生成）
- ⬜ 一致性检查（未执行）

上次修改时间：2026-05-10 16:30

下一步：复杂度评估 → PRD 生成
是否继续？
```

**第三步：从断点继续**

- 跳过已完成并确认过的 HARD-GATE 节点
- 从下一个未完成的节点开始
- 如果有 dirty 产物（标记为需重新生成），先提示用户是否需要处理

### 恢复模式注意事项

- 恢复时不重新创建目录或 `input.md`
- 如果 `project-state.json` 损坏或不可解析，提示用户是否从头开始
- 如果 `lifecycleStatus` 为 `delivered`，提示用户项目已完成，询问是否进入变更模式
