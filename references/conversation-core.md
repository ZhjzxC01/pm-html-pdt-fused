# 对话式工作流 — 核心规则

用途：定义默认全流程的对话推进方式、自动初始化、澄清规则、功能清单、复杂度评估、增量修改和回复结构。

## 核心规则

1. 默认单节点推进：`自动初始化 -> 原始资料处理（如有）-> 对话澄清（如有）-> 功能清单 -> 复杂度评估 -> 原型 -> PRD -> 标注 -> 一致性检查 -> 业务确认单（可选）-> 上线交付包（可选）`。
2. `功能清单`、原型、`PRD`、标注完成后必须暂停，等待用户明确确认。
3. 用户提出修改意见时，优先修当前节点，不越级生成后续产物。
4. 新项目少追问，能从需求推断的项目名、类型、业务对象、关键页面和审批流开关应先自动补齐。
5. 回复必须包含当前节点、产物路径、本轮摘要、待确认点和下一步建议。

## 自动初始化

首次收到用户需求时，在进入功能清单之前，先自动完成项目目录初始化：

1. 从需求内容推断项目目录名，使用英文短横线命名（如 `contract-approval`、`hr-onboarding`）。
2. 在当前工作目录下创建 `<project-name>/`、`<project-name>/output/` 和 `<project-name>/raw-materials/` 目录。
3. 将用户原始需求写入 `<project-name>/input.md`。
4. 生成空的 `<project-name>/project-state.json`。
5. 如果推断的目录已存在，直接复用，不覆盖已有文件。
6. 如果用户在对话中提供了附件（截图、文档、表格等），将其保存到 `<project-name>/raw-materials/` 目录。
7. 初始化完成后，在回复中告知用户已创建的目录路径。如果检测到原始资料，进入原始资料处理节点；否则直接进入功能清单节点。

初始化回复示例（无原始资料）：

```markdown
当前节点：自动初始化
产物：
- contract-approval/input.md（已写入需求原文）
- contract-approval/project-state.json（空状态）
- contract-approval/raw-materials/（原始资料目录，当前为空）
- contract-approval/output/（输出目录）

已自动创建项目工作目录，正在进入功能清单整理...
```

初始化回复示例（有原始资料）：

```markdown
当前节点：自动初始化
产物：
- procurement-approval/input.md（已写入需求原文）
- procurement-approval/project-state.json（空状态）
- procurement-approval/raw-materials/（已保存 3 份原始资料）
- procurement-approval/output/（输出目录）

已自动创建项目工作目录，检测到原始资料，正在进入资料处理...
```

## 原始资料处理

当 `raw-materials/` 目录中存在文件时，在进入功能清单之前，先完成原始资料处理：

1. 逐份读取 `raw-materials/` 中的所有文件。
2. 根据文件类型采用不同策略提取信息：
   - **图片**（`.png`/`.jpg`/`.jpeg`/`.gif`/`.webp`）：通过 AI 视觉能力识别图中的文字、流程图、表格等内容，提取角色、流程、规则等关键信息。
   - **Word 文档**（`.docx`/`.doc`）：读取文档全文，提取业务规则、流程描述、角色定义、字段说明等。
   - **Excel 表格**（`.xlsx`/`.xls`）：读取表格数据，提取枚举值、配置项、数据字典、阈值规则等。
   - **PDF 文档**：读取文档内容，提取业务规则、流程说明、制度条款等。
   - **Markdown / 纯文本**（`.md`/`.txt`）：直接读取，提取结构化信息。
3. 将每份资料的关键信息整理成结构化摘要，包含：提取到的角色、流程步骤、业务规则、字段定义、阈值条件、特殊约束等。
4. 标注每条信息的来源文件，确保可追溯。
5. 执行结构化冲突检测，逐项检查：
   - **数值冲突**：阈值、金额、数量、限制是否与需求文本不一致
   - **角色冲突**：角色名称、职责描述是否与需求文本矛盾
   - **流程冲突**：流程步骤、顺序、分支条件是否与需求文本不一致
   - **字段冲突**：字段名、类型、枚举值是否与需求文本不一致
   - **规则冲突**：业务规则（如审批条件、计算公式）是否与需求文本矛盾
6. 识别出资料中存在但需求文本中未提及的补充信息。
7. 整理完成后暂停，向用户展示摘要、**冲突清单**和待确认问题，等待用户确认。

## 对话澄清

原始资料处理完成后（或没有原始资料时直接从自动初始化后），如果存在以下情况，进入对话澄清：

1. 原始资料中提取到的信息与需求文本存在矛盾。
2. 原始资料中提到了需求文本未覆盖的关键业务规则。
3. 需求文本中存在模糊表述，需要明确具体参数（如阈值金额、审批节点数量、角色范围等）。
4. 缺少阻塞功能清单生成的关键信息（如核心业务对象不明确、状态机缺少终态定义等）。

澄清原则：
- **一次只问一个问题**，不要一次性抛出多个问题让用户批量回答。
- **多选优先**：默认用结构化多选题提问，而非开放性问题。格式为：
  - 列出 2-4 个选项（A/B/C/D），每个选项附一句话说明
  - 标注推荐选项及推荐理由
  - 保留"其他"选项让用户自由输入
  - 每轮**必须追加**一个固定选项：`E. 需求已澄清，可以继续`——选择此项表示用户认为需求信息已充分，结束澄清阶段进入功能清单
  - 示例见下方
- 能从已有信息推断的不问。
- **提问优先级**：按阻塞程度排序，先问阻塞功能清单的核心问题，再问影响原型设计的问题，最后问影响 PRD 精度的细节：
  1. 核心业务对象不明确、状态机缺少终态 → 最高优先
  2. 页面结构、交互模式、审批流设计 → 高优先
  3. 阈值金额、枚举值、权限范围 → 中优先
  4. 文案措辞、颜色偏好、按钮位置 → 低优先，可延后到对应节点确认
- 不阻塞当前节点的细节留到后续节点再确认。
- **不限轮数**，持续提问直到用户主动选择"需求已澄清，可以继续"。
- 用户回答后立即处理，再问下一个问题（如有未澄清项）。
- 如果连续 2 轮用户都选了"其他"且未给出明确补充，主动总结当前已确认信息和仍待补充项，询问是否可以继续。

### 非功能需求检查点

当需求涉及以下场景时，主动询问非功能需求（不阻塞功能清单，但需记录）：

| 场景 | 需要确认的非功能项 |
|------|-------------------|
| 数据量大（预计 >10 万条） | 分页策略、查询性能、索引设计 |
| 多角色/多部门使用 | 并发量级、数据隔离级别 |
| 涉及财务/审批/合同 | 审计日志要求、数据加密、操作留痕 |
| 涉及导入导出 | 文件大小限制、并发导入限制 |
| 涉及消息通知 | 通知延迟容忍度、通知渠道 |

非功能需求不阻塞功能清单生成，记录到 `pendingQuestions` 中，在 PRD 阶段补充。

多选提问示例：

```markdown
根据需求描述，推测核心业务对象可能是以下几组：

A. 报销单 + 审批流 + 费用明细（标准报销）
B. 报销单 + 审批流 + 费用明细 + 预算管控（含预算管理，推荐）
   推荐理由：覆盖核心场景且范围可控
C. 报销单 + 审批流 + 费用明细 + 预算管控 + 差旅集成（完整版）
D. 其他（请补充）
E. 需求已澄清，可以继续

选择哪个？
```

所有关键信息确认后，汇总确认结果。检查是否需要范围分解，然后进入功能清单节点。

## 范围分解

在进入功能清单之前，评估需求是否涉及多个相对独立的子系统。如果满足以下任一条件，先提出分解建议：

### 触发条件

1. 需求涉及 3 个以上独立业务域（如审批、报表、消息中心、日程管理）
2. 预估功能点超过 30 个或页面超过 15 个
3. 用户明确提到"整个 XX 系统"或"平台"等大范围词汇
4. 不同子系统之间仅有松耦合（如通过消息通知或共享用户关联）

### 分解方式

1. 识别需求中的独立子系统，按业务域分组
2. 识别子系统间的依赖关系（强依赖 vs 松耦合）
3. 按业务价值和依赖顺序排列子项目优先级
4. 向用户展示分解方案，等待确认

### 分解示例

```markdown
这个需求涉及 4 个相对独立的子系统，建议拆分为子项目逐个交付：

子项目 1: 审批系统（核心，优先级最高）
  - 独立闭环，其他子系统的基础
子项目 2: 报表系统（依赖审批数据）
  - 需要审批系统完成后才有数据可报
子项目 3: 消息中心（独立模块）
  - 可与审批系统并行开发
子项目 4: 日程管理（独立模块）
  - 最低优先级

建议从子项目 1 开始，每个子项目独立走完整闭环（功能清单→原型→PRD→标注→一致性检查）。
选择哪个子项目开始？或选择"全部一起做"（不推荐，范围过大）。
```

### 不分解的情况

- 需求明确是单模块改动
- 子系统之间强耦合，拆分会破坏整体性
- 用户明确要求一次性完成

## 功能清单

对话澄清完成后（或无需澄清时直接从原始资料处理后），进入功能清单整理。

### 多方案提议

当需求存在多种可行的实现路径时，必须在功能清单中提出 2-3 种方案并给出推荐：

- **方案描述**：每种方案用 2-3 句话说明核心思路。
- **优劣对比**：列出每种方案的优势和劣势。
- **推荐方案**：明确推荐哪种方案，说明推荐理由。
- **用户决策**：等待用户选择后再确定功能清单内容。

适用场景举例：
- 审批流设计：简单流转 vs 带条件分支的状态机 vs 多级嵌套审批
- 数据管理：单表 vs 主子表 vs 关联表
- 权限模型：角色级权限 vs 数据级权限 vs 混合模式
- 页面结构：单页 Tab 切换 vs 多页面跳转 vs 抽屉/弹窗详情

如果需求路径唯一（没有合理替代方案），直接给出功能清单，不需要强行凑方案。

用户确认方案后，输出完整功能清单并等待确认。

### 功能分组与 Backlog 持久化

功能清单确认后，根据优先级矩阵将功能分为 MVP / 增强 / 优化 / 排除四组（详见"优先级排序"章节），并将分组结果写入 `project-state.json` 的 `backlog` 字段。恢复项目时展示完整 backlog，用户可调整优先级。

## 复杂度评估

功能清单确认后，在生成原型之前，自动执行需求复杂度评估：

1. 根据需求涉及的页面数量、审批流复杂度、角色数量、外部系统依赖、数据迁移等因素，评估需求级别为 S / M / L。
2. 评估结果包含：级别（S/M/L）、判定理由、评估因素列表。
3. 评估完成后暂停，向用户展示评估结果和建议使用的 PRD 模板，等待用户确认。
4. 用户可以接受建议级别，也可以手动指定其他级别。
5. 确认后进入原型生成节点。**评估结果影响原型生成策略**：S 级只生成核心页面原型（1-3 个关键页面），M 级生成完整模块原型，L 级生成全量页面原型。

S/M/L 级别定义：

- **S 级（轻量需求）**：单页面/单字段改动、不改变核心流程、不涉及审批流/外部系统/复杂权限。PRD 使用轻量需求卡模板（8 个章节）。
- **M 级（中等复杂度）**：单模块新功能或多页面联动、局部流程调整、涉及权限/导入导出/报表/外部接口。PRD 使用功能版模板（17 个章节）。
- **L 级（大型复杂需求）**：跨多个业务系统、核心主数据、复杂审批流/状态机、数据迁移、第三方强依赖、性能/安全/合规要求。PRD 使用完整版 B 端 PRD 模板（21 个章节）。

### L 级 PRD 分章节确认

L 级 PRD 章节多（21 个），一次性生成后确认压力大。采用分段确认：

1. **第一批（核心章节，约 7 章）**：基本信息、背景与目标、角色与权限、业务流程、页面设计、字段与枚举、业务规则。生成后暂停，等待确认。
2. **第二批（技术章节，约 7 章）**：状态机、数据处理、接口设计、异常处理、导入导出、报表统计、通知规则。生成后暂停，等待确认。
3. **第三批（收尾章节，约 7 章）**：非功能需求、数据模型、上线计划、测试验收、培训方案、风险评估、变更记录。生成后等待最终确认。

每批确认时，用户可以：
- 通过：继续下一批
- 修改：指出具体章节问题，修复后继续
- 跳过：直接看全部完成后的版本

S 级和 M 级不需要分章节确认，一次性生成并确认即可。

### 原型方案对比（可选）

对于信息架构有重大差异的关键页面（如列表页用表格 vs 看板、详情用弹窗 vs 新页面），在原型生成前提供 2 种布局方案的文字描述对比，让用户选择后再生成完整原型。

触发条件（满足任一）：
- 页面存在 2 种以上合理的布局模式
- 用户在澄清阶段表达了对布局的不确定性

不触发条件：
- 页面布局只有一种合理方案（如审批详情页用弹窗是行业惯例）
- S 级需求（简化流程，不做方案对比）

## 推荐回复结构

```markdown
当前节点：功能清单
产物：workspace/功能清单.md
摘要：已补齐业务对象、状态机、关键页面和待确认问题。
请确认是否继续生成原型；如需修改，请直接指出模块或规则。
```

## 业务确认单（可选）

一致性检查通过后，询问用户是否生成业务确认单。

生成规则：
- 从 PRD 提取关键信息，转化为业务语言
- 去除所有技术术语
- 流程图使用简单方框箭头
- 输出：`<project>/output/业务确认单.md`
- 生成后等待业务方确认

## 上线交付包（可选）

业务确认单确认后（或用户跳过业务确认单后），询问用户是否生成上线交付包。

生成规则：
- 包含：权限配置清单、字典配置清单、上线 Checklist、培训大纲
- 输出：`<project>/output/上线交付包.md`
- 生成后更新 lifecycleStatus 为 delivered

## 增量修改

当用户在任意节点提出修改意见时，执行以下流程：

### 第一步：识别修改类型

| 修改对象 | 影响范围 | 是否需要回退 |
|----------|----------|-------------|
| 纯文案修改（按钮文字、提示语、标签） | 仅原型 | 原型 dirty，PRD/标注不动 |
| 单字段规则修改（阈值、校验、枚举） | 原型 + PRD 对应 section | 原型 + PRD dirty，标注不动 |
| 新增/删除字段 | 模块 → 原型 → PRD → 标注 | 原型 + PRD + 标注 dirty |
| 新增/删除模块 | 页面 → 原型 → PRD → 标注 → 一致性检查 | 全部 dirty |
| 新增/删除页面 | 原型 → PRD → 标注 → 一致性检查 | 全部 dirty |
| 状态机/审批流修改 | PRD → 原型 → 标注 → 一致性检查 | 全部 dirty |
| 设计体系变更（配色、字体、组件风格） | 原型 → 标注（PRD 不动） | 原型 + 标注 dirty |
| 不涉及上游的纯样式修改 | 无 | 无需回退 |

### 第二步：展示影响并等待确认

向用户明确说明：
1. 修改了什么
2. 哪些下游产物会受影响（dirty 标记）
3. 推荐的处理方式（自动重生成 vs 手动处理）

### 第三步：执行修改

修改上游产物后：
- 如果用户选择自动重生成：按依赖顺序重新生成所有 dirty 产物，跳过中间 HARD-GATE，但最终产物需要用户确认
- 如果用户选择手动处理：只修改指定产物，dirty 产物在下次一致性检查时会提示过期

## 需求来源多样化

支持从多种来源提取需求信息。

### 支持的需求来源

| 来源类型 | 输入方式 | 处理策略 |
|----------|----------|----------|
| 自由文本 | 对话框直接输入 | 走标准需求结构化流程 |
| 原始资料文件 | 图片/Word/Excel/PDF/Markdown | 保存到 raw-materials/，提取关键信息 |
| 任务卡片 | Jira/飞书/Linear 导出的 JSON 或 CSV | 解析任务字段，提取需求描述、优先级、负责人 |
| 竞品截图 | 竞品产品截图 | 视觉识别功能点，提取功能差异 |
| 合规文档 | 行业标准/合规要求文档 | 提取约束条件、必须满足的合规要求 |
| 用户反馈汇总 | 用户反馈表格 | 聚类分析高频问题，提取需求点 |

## 优先级排序

功能清单生成后，自动提供优先级建议。

### 优先级矩阵

| 维度 | 评估标准 |
|------|----------|
| 业务影响 | 高：直接影响核心业务流程 / 中：提升效率但不阻断 / 低：体验优化 |
| 实现难度 | 简单：单页面改动 / 中等：多页面联动 / 复杂：跨模块或涉及外部系统 |
| 紧急程度 | 高：用户强烈要求或阻断业务 / 中：计划内需求 / 低：锦上添花 |

### 功能分组建议

基于优先级矩阵，将功能分为三组：

| 分组 | 定义 | 建议 |
|------|------|------|
| MVP（第一期） | 业务影响高 + 实现难度简单或中等 | 必须在第一期交付 |
| 增强（第二期） | 业务影响中 + 实现难度中等 | 第一期上线后 2-4 周内交付 |
| 优化（后续） | 业务影响低 或 实现难度复杂 | 视用户反馈决定是否做 |

## 多项目关联

当需求涉及跨模块引用时，识别并处理多项目关联。

### 触发条件

- 用户提到"报销系统需要关联合同系统的合同编号"
- 需求涉及引用其他模块的主数据或业务数据
- 用户明确提到需要跨系统关联

### 处理方式

1. **识别跨项目实体引用**：标记哪些字段引用了外部模块的实体
2. **记录关联关系**：在 `project-state.json` 中记录跨项目引用
3. **关联一致性检查**：检查引用的字段名、类型是否与目标项目一致
4. **PRD 标注**：在 PRD 中明确标注跨项目引用的字段和数据来源
5. **跨项目一致性检查**：在一致性检查阶段，额外检查：
   - 引用的字段名是否与目标项目的字段名一致
   - 引用的字段类型是否兼容（如目标项目是 string，本项目不能当 number 用）
   - 引用的枚举值是否在目标项目中存在
   - 如果目标项目不存在或无法读取，标记为 warning 并建议用户手动确认

## CLI 定位

- 对普通产品工作，默认不要求用户手动敲命令。
- 对本地复现、批量生成、校验、调试和测试，使用 `pnpm dev -- ...`。
- CLI 输出结果需要转化成产品经理能读懂的摘要，而不是只贴命令日志。
