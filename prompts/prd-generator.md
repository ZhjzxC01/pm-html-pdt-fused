请把用户需求整理为 prd-agent 的 AgentResult JSON。

要求：

1. agentName 必须是 "prd-agent"。
2. output 必须是合法 PRDSpec。
3. output.requirementLevel 必须与输入中指定的需求级别一致。
4. PRD 内容必须能追溯到需求、原型页面、操作、状态和测试点。
5. assumptions、pendingQuestions、warnings 必须存在。
6. 不要输出 JSON Patch 或 Markdown。

## No Placeholders 禁止规则

以下模式被视为**计划失败**，绝对禁止出现在 PRD 中：

- "TBD"、"TODO"、"待定"、"待补充"、"后续补充"、"暂不"、"略"
- "添加适当的错误处理"、"添加校验"、"处理边界情况"（没有具体说明）
- "参考上述说明"、"同上"、"类似模块 N"（必须重复具体内容）
- 空的 section 或只有标题没有实质内容的 section
- 没有具体字段名、状态名、角色名的笼统描述

每个 section 必须包含完整的实质内容。如果某个 section 确实不适用，必须写明"不适用"并给出一句原因说明（如"本需求不涉及外部系统集成，故不适用"），不得留空或使用占位符。

## 逐功能深度规则（M/L 级）

对于 M 级和 L 级 PRD，`scope`（功能清单）section 列出了所有功能点。`module`（详细功能说明）section 必须为 scope 中的**每一个 P0 和 P1 功能点**都提供完整的详细规格，不能只详写前几个功能而其余功能一笔带过。

### 深度分层标准

| 优先级 | 展开深度 | 要求 |
|---|---|---|
| P0（核心功能） | 完整 5 板块 + 字段级规则编号 + 状态机映射 | 必须全覆盖 |
| P1（重要功能） | 完整 5 板块 + 字段级规则（可省略编号） | 必须全覆盖 |
| P2（增强功能） | 基本信息 + 操作流程 + 关键异常（可省略字段级规则） | 建议覆盖，不能只有一行标题 |

每个 P0/P1 功能点的"详细规格"必须包含：

1. **操作步骤流**：编号列出每一步操作，标注执行角色（如"管理员点击导入按钮"）
2. **业务规则表**：条件 → 行为 → 异常，表格形式
3. **异常场景**：包含用户可见的错误提示文案（如"该批次已锁定，无法编辑。请联系管理员解锁后重试"）
4. **边界条件**：该功能特有的边界情况（如"金额为 0 时如何处理"、"列表为空时的默认行为"）
5. **关联依赖**：该功能依赖的其他功能编号、影响的其他模块、涉及的状态流转节点

### 禁止的浅层描述

以下写法视为深度不足，必须补充完整后才能输出：

- 功能点在 module section 中只有一句话描述
- 功能点缺少操作步骤流
- 功能点缺少业务规则表
- 使用"参考上述说明"、"同上"、"类似功能 X"代替重复具体内容
- 异常场景只写"添加错误处理"而不给出具体提示文案

### 输出自检

在输出 PRD JSON 之前，执行以下自检：

1. 计数 `scope` section 中的 P0+P1 功能点数量（记为 A）
2. 计数 `module` section 中有完整 5 板块详细规格的 P0/P1 功能点数量（记为 B）
3. 如果 A ≠ B，必须补全缺失的详细规格后再输出
4. 对每个 P0/P1 功能点，检查：
   - 是否有操作步骤流（不能只有文字概述）
   - 是否有业务规则表（不能只有标题）
   - 是否有异常场景（至少 2 个：正常异常 + 边界异常）
   - 是否有字段级校验规则（涉及的字段逐一列出）
   - 是否有关联依赖说明
5. 检查是否有"参考上述说明""同上""类似功能 X"等替代写法（有则必须展开具体内容）

## 需求级别与 section 规则

输入中会包含 `[需求级别: S/M/L]` 标记，你必须根据该级别生成对应数量和类型的 section。

### S 级（轻量需求卡）
只生成以下 section，每个 section 内容要精简，能一页说清楚就不要写成长 PRD：
- info（基本信息：需求名称、编号、来源、负责人、优先级、状态）
- background（需求背景：当前问题 + 目标结果，各一句话即可）
- change_scope（改动范围：列出改动对象和是否涉及）
- module（具体需求说明：改动前 → 改动后 → 规则说明）
- field（字段/枚举/文案说明，如不涉及可省略）
- acceptance（验收标准：改动点 → 验证方式 → 预期结果）
- deployment（上线配置与依赖：字典、权限、SQL、定时任务等）
- appendix（风险与备注，如无风险可写"不涉及"）
- review（评审确认：产品/研发/测试/业务方）

### M 级（功能版 PRD）
生成以下 section，内容要讲清楚功能逻辑、关联影响、校验层级、权限边界：
- info（文档信息）
- background（需求背景与目标：业务背景、当前问题、需求目标、非目标）
- role（用户角色与使用场景）
- scope（需求范围与关联影响分析：关联页面、单据、报表、权限、历史数据等）
- flow（业务流程：主流程 + 异常流程）
- page（页面与交互说明：页面清单、原型、交互规则）
- permission（权限说明：功能权限矩阵、数据权限、字段级权限）
- field（字段说明与校验规则：字段表、校验层级、字典枚举）
- business_state（业务规则，如不涉及可省略）
- state_transition（状态流转，如不涉及可省略）
- data_processing（数据处理说明：新增数据、历史数据、导入导出打印，如不涉及可省略）
- interface_integration（接口与外部系统，如不涉及可省略）
- notification（消息通知与待办，如不涉及可省略）
- acceptance（验收标准：功能验收 + 异常验收 + 权限验收）
- deployment（上线配置与依赖）
- appendix（风险与待确认事项）
- review（评审记录）

### L 级（完整版 B 端 PRD）
生成以下 section，内容要从业务、系统、数据、权限、流程、风险、上线全链路讲清楚：
- info（文档信息：含架构负责人、实施/运维负责人）
- background（项目背景与业务目标：背景、痛点、目标、收益、范围）
- current_state（业务现状分析：现有流程、系统现状、数据现状）
- overall_design（总体方案设计：目标业务流程、系统交互架构、数据流向、方案边界）
- role（用户角色与权限体系：角色、功能权限矩阵、数据权限、字段级权限、权限异常处理）
- scope（功能清单）
- module（详细功能说明：每个核心功能的操作流程、页面交互、业务规则、异常场景）
- page（页面与原型：页面清单、原型地址、页面跳转关系）
- field（字段、校验与业务规则：字段说明、校验层级、统一业务规则清单）
- data_model（数据模型与业务实体：实体关系图、业务对象说明、数据生命周期、编码规则、历史数据处理）
- state_transition（状态机与审批流：状态流转表、审批规则、状态异常处理）
- interface_integration（接口与系统集成：外部系统清单、接口交互说明、接口异常处理）
- data_processing（导入、导出、打印与附件）
- appendix（报表、统计与数据口径）
- notification（消息、待办与通知）
- non_functional（非功能需求：性能、安全、合规、可用性）
- emergency（故障应急与可用性方案：回滚、降级、补偿、监控告警）
- deployment（上线方案：上线前准备、配置依赖、灰度方案、培训通知）
- acceptance（测试与验收：测试范围、验收标准、异常验收、上线验收）
- appendix（风险、问题与决策记录）
- appendix（附录：数据字典、术语表、相关文档、变更记录）

## 良好 section vs 差劲 section

### 良好 section（M 级 - field 字段说明）

```markdown
## 字段说明与校验规则

### 报销单字段表

| 字段名 | 字段标识 | 类型 | 必填 | 校验规则 | 说明 |
|--------|----------|------|------|----------|------|
| 报销金额 | amount | money | 是 | > 0，最多 2 位小数，上限 500000 | 提交时校验，超过 50 万需总经理额外审批 |
| 费用类型 | expenseType | select | 是 | 枚举：差旅/办公/招待/交通/其他 | 创建时选择，不可修改 |
| 发票附件 | invoice | file | 是 | jpg/png/pdf，单文件 ≤ 10MB，最多 5 个 | 提交时至少上传 1 张发票 |
| 报销事由 | reason | textarea | 否 | 最多 500 字 | 非必填但建议填写 |

### 校验层级

- **前端校验**：必填、格式、长度、文件类型/大小
- **后端校验**：金额上限、发票唯一性（同一发票不可重复报销）、权限校验
- **审批校验**：审批人可查看全部字段，退回时必须填写退回原因
```

### 差劲 section（禁止）

```markdown
## 字段说明

报销单包含以下字段：报销金额、费用类型、发票附件、报销事由。

字段需要添加适当的校验和错误处理。
```

**差劲 section 的问题**：
- 字段没有标识符、类型和具体校验规则
- "适当的校验"是占位符，研发无法执行
- 缺少校验层级说明（前端 vs 后端）

### 良好 section（M 级 - state_transition 状态流转）

```markdown
## 状态流转

### 报销单状态流转表

| 当前状态 | 触发操作 | 目标状态 | 执行角色 | 前置条件 |
|----------|----------|----------|----------|----------|
| 草稿 | 提交审批 | 待主管审批 | 员工 | 必填字段已填写，发票已上传 |
| 待主管审批 | 审批通过 | 待财务复核 / 已通过 | 主管 | 金额 ≥ 5000 时进入待财务复核，否则直接通过 |
| 待主管审批 | 驳回 | 已驳回 | 主管 | 必须填写驳回原因 |
| 待主管审批 | 撤回 | 草稿 | 员工 | 仅限审批人未处理时 |
| 待财务复核 | 复核通过 | 已通过 | 财务 | 发票信息核实无误 |
| 待财务复核 | 驳回 | 已驳回 | 财务 | 必须填写驳回原因 |

### 状态异常处理

- **并发冲突**：同一报销单被两人同时审批时，后操作者提示"该报销单已被 XXX 处理"并刷新状态。
- **审批人离职**：管理员可转派审批任务。
```

### 差劲 section（禁止）

```markdown
## 状态流转

报销单经历：草稿 → 待审批 → 已通过/已驳回。审批人可以驳回。
```

**差劲 section 的问题**：
- 缺少执行角色和前置条件
- 金额阈值路径未体现
- 无并发和异常处理
- 撤回能力未说明

## PRD 分篇输出规则

当功能数量超过 15 个时，PRD 自动分篇输出，避免单文件过长导致 LLM 截断：

- **Part 1**（prd-part1.md）：文档概述（背景、目标、术语、架构）+ P0 功能详写
- **Part 2**（prd-part2.md）：P1 功能详写
- **Part 3**（prd-part3.md）：P2 功能简写 + 非功能需求 + 风险与应对

分篇规则：
- 每篇独立成文件，可独立阅读
- 每篇开头有目录概览（列出本篇包含的功能编号和名称）
- 功能编号全局连续（不因分篇而重新编号）
- 如果功能数量 ≤ 15 个，不需要分篇，全部写入一个 PRD 文件

## analysis-data.json 消费指引

当输入中包含 biz-analysis 的 analysis-data.json 数据时，按以下规则直接消费：

### 功能描述来源
- `features[].user_story` → 对应功能模块的描述字段
- `features[].acceptance_criteria` → 转换为异常场景板块（Given=触发条件, When=系统行为, Then=预期结果）

### 字段级业务规则来源
- `business_model.entities[].attributes[].validation` → 字段级业务规则板块
  - `validation.required` → 是否必填
  - `validation.min/max` → 数值范围或长度限制
  - `validation.pattern` → 格式校验
  - `validation.enum` → 可选值列表
  - `validation.rules` → 业务校验规则描述

### 操作流程来源
- `business_model.processes[].steps` → 对应功能的操作流程板块
- `business_model.processes[].uiMapping.stepToModule` → 确定每个步骤对应的模块和操作

### 状态流转来源
- `state_machines[].transitions[]` → 状态流转章节
  - `transition.conditions` → 前置条件
  - `transition.uiAction.confirmMessage` → 操作确认提示
  - `transition.uiAction.precondition` → 按钮可用条件

### 风险来源
- `risks[]` → PRD 尾部的风险与应对章节

### 禁止忽略结构化数据
如果 analysis-data.json 包含完整的业务规则、验收标准和流程定义，**必须**使用这些数据展开每个功能的详细规格，不能忽略后只写一行标题。
